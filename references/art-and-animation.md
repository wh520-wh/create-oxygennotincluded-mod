# 原版风格美术与技术美术

## 参考与设计

查看目标游戏中至少两台相近原版设备：同用途及同尺寸各一台。用合法取得的游戏截图或用户截图研究风格，不把原版资源直接重新打包为自有美术。记下轮廓、色板、光向、材质、结构与像素密度；别只写一句“卡通风格”。

《缺氧》不是单纯低分辨率像素画。保持带手绘变化的工业卡通，避免光滑写实 3D、纯矢量仪表图、整齐重复圆角矩形或高饱和塑料质感。装饰应解释机器结构而非堆贴随机噪点。

先画可信结构：承重底座、主功能部件、输入输出路径、传动/电气系统、控制面板、检修结构。大轮廓可一眼识别用途，小细节不挤掉主体。区分建材外观与实际运行耗材；例如消耗钢的面板别无意写成只有铁的说明。

## 逐轮打磨

1. 构图：轮廓、比例、重心、负空间，保留用户指定外形。先定格子与地板基线。
2. 结构：法兰、支架、焊缝、轴承、螺丝、管接头、维修盖板，解决“零件为何连在这里”。
3. 材质：统一光向；外轮廓强、内线弱；金属边缘高光、遮挡阴影、有限色阶、少量划痕/磨损，减少大片平涂。玻璃有边框厚度、反光与内部液面；液体保持水平。
4. 精修：手绘线条变化、局部不对称细节与可辨识标记，避免让轮廓歪到破坏格子校准。文字在实际缩放仍需清楚，读不清则用图形标识。
5. 动效：待机/工作/停机变化体现功能；故障、建造等状态按原生消费路径补齐，不一律臆造银行名。活动部件分层，遮挡与轴心可信。
6. 同场对照：并排放原版，检查线宽、饱和度、细节密度和比例；常用缩放看可读性，放大看边缘，缩略图看辨识度。发现不协调就再改，不以“已经生成”结束。

## 资源结构

查看目标版本加载器及原版相近 KAnim。核对目录名、资源注册名、atlas、build.bytes 与 anim.bytes 的关系；若加载器追加 _kanim，目录不要再带后缀。不要仅以文件存在判定资源可加载。

区分 animation bank/state 与 build symbol。创建名为 ui 的动画不自动提供名为 ui 的符号。验证 Def.GetUISprite 等 UI 查找路径需要的符号或正确专属绑定；按资源局部命名空间管理通用 symbol，不为避免重名把所有 ui 符号随意改成不可查找的名字。

检查实际需要的 idle、working、off、ui、place、construction、operating/互动等状态及 symbol overrides；这些名字依对象而异，必须查消费者。物品瓶/罐/碎块与建筑使用不同动画约定，不要拿一个液滴图凑所有状态。

使用 ImageGen、手绘或程序绘图均可，但静态概念图只是输入。加工为真正透明分层图元、统一轴心、图集和原生动画，并保留编辑源。修改既有矢量/代码生成美术时优先原生编辑；生成位图参考按可用图像技能执行。

自制二进制写入器检查格式版本、UV、symbol hashes、frame索引、排序、变换、帧率、loop、边界、atlas padding 和透明色。结构正确不能证明游戏缩放正确。

## 格子与几何验收

- 以原版格子大小、KAnim 内部单位、controller scale、build frame、anim matrix 和 BuildingDef 为一套链路测量；不要假设画布每 100 像素一定就是一格。
- 区分画布尺寸、非透明图形包围盒、动画边界和实际占地。透明边距不能充当机器高度。
- 对齐底座到地板顶面、水平中心与奇偶宽度原点；检查整格/半格偏移。绘制带格子、地板与占地框的对照图，再进游戏验证。
- 主体接近设计占地；留白和镂空合理但不得视觉悬空、越界穿墙或为了修图而改成错误实心占格。
- 测量整个工作循环最大包围盒，活动零件不得穿过天花板、墙或相邻机器。不要把整台机器绕画布中心摇摆；只移动正确部件。
- 检查输入输出口、线缆、自动化口、状态图标、小人互动站位和翻转后的变化。

## 图标与菜单图

能显示不等于做正确。问号消失后继续检查：能否被查找、尺寸是否合适、是否居中、是否遮挡邻近条目、不同界面缩放下是否可读。建造菜单、研究界面、选择面板、世界内与地面物品可能使用不同符号、动画与缩放规则，逐入口验收；一个入口正常不能证明其他入口正常。元素小图标不能替代瓶罐的完整容器动画。

菜单图不是建筑图。建筑动画有自己的占地、地板基线和位置偏移，把整套建筑图及参数直接搬进菜单会得到错误结果。菜单图单独设置图像尺寸、符号尺寸、动画边界和偏移；某次方案用过的具体数字（如居中的 128×128 图标）只是那个项目的做法，不能规定所有 Mod 照用，按目标版本原生菜单的实际消费路径核对。

只缩小 PNG 可能仍然显示过大：显示大小还受图集 UV、符号几何、ANIM 边界和变换矩阵影响。修复图标同步核对图片、UV、符号几何、动画边界与位置偏移五项；图片已缩小不能证明游戏里会缩小。

资源生成代码常被多个对象共用。一处图标生成错误要追查共用生成器，检查全部使用同一流程的对象（本次教训：问题出现在发电机截图，反应器与三个元素图标由同一套代码生成）；修复范围以共同原因决定，不以截图里出现的对象决定。

## 建造阶段美术

建造蓝图与成品必须分别制作和验收。补齐 place、construction 等状态名称不等于完成——这些状态直接复用成品建筑图层时，资源结构完整，放置时仍显示完整填色、金属阴影和运行部件，没有原版蓝图线稿效果。

1. 对照目标版本同类原版建筑，确认放置预览、待建蓝图、施工过程和建造完成分别使用哪些动画、符号和渲染机制。
2. 放置预览符合原版线稿表现，保留外轮廓和必要结构线；不要简单把成品图降低透明度作为替代。
3. 核对预览颜色、透明度以及可放置/不可放置提示由游戏控制还是资源提供，避免重复着色或破坏原生提示。
4. 待建与施工状态分别按原版机制实现，不默认两者与放置预览完全相同。
5. 蓝图、施工与成品保持占地、原点、缩放、管口位置及地板基线一致，避免建造前后跳位。
6. 检查运行灯光、液面、调优标记等部件是否应出现在各阶段，未建成建筑不得呈现正在运行的外观。

验收：与同类原版建筑并排比较，覆盖鼠标放置预览、无效位置、待建任务、施工过程和建造完成。仅确认状态名称存在或资源解析通过不能判定完成；没有游戏实测时标记“建造阶段视觉待验证”。

## 必须保留的验收证据

至少保留：原版并排对比、格子占地及地板对齐、普通缩放、放大细节、菜单图标、各显示入口（建造菜单、研究、选择面板、世界内、地面物品）实际截图、全部主要状态动画，以及可搬运物外观（适用时）。修复缺陷时保留差量证据：与上一版本比较本次不应受影响的内容（本次教训：全部非 ui 动画逐字节相同、DLL 相同）。

逐项评判：结构可信 / 风格协调 / 信息清楚 / 技术对齐 / 动效正确。任何一项不通过就继续精修。不能声称与 Klei 一模一样；应给用户可审查的实际图和差异。没有游戏环境只能给出资源检查结论并写“游戏显示待确认”，不得宣称已解决真实游戏错位。
