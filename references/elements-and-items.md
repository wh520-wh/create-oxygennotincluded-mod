# 元素与物品

## 1. 分清四种对象

分别设计环境中的 Element、渲染与动画 Substance、可搬运实体 Prefab、供 UI/配方/储存查询的 Tag。确认四者身份对应且索引有效。液气从模拟格子进入 Storage 往往需要物品实体；“液体能流”不能证明“能擦拭成瓶”。

在目标程序集检查 IOreConfig、EntityTemplates.CreateLiquidOreEntity / CreateGasOreEntity / CreateSolidOreEntity 及配置加载流程。按目标版本的原生路线注册，不只调用创建方法却不进入资源注册。液体按需要检查目标版本原生装瓶机制、容器动画、拾取、堆叠、温度疾病和原生相变监视组件；参考实现中的组件（例如参考 Mod 自制的 BottleFlipper）先追查来源、用途和依赖，确认是原版通用需求还是参考项目独有机制。不要把示例 API 当所有版本通用。

为食物、药品、种子、工业产品、装备分别选对应原生配置与扩展，而不是一律用裸 GameObject。原生基础模板承担可选中、保存、碰撞、掉落、拾取等行为；核对其默认值是否符合新物品。

## 2. 身份与加载

- 使用稳定、独有的字符串 ID。确认游戏是对字符串做哈希，还是在具体字段解析枚举，逐字段验证。
- 禁止把元素的十进制哈希数字当 elementId 字符串。它可能再次哈希，导致 Element 与 Substance 查找错位。
- 对比 element.id、element.tag、substance.elementID、substance.name/nameTag、PrefabID、实体 PrimaryElement 和消费标签。物质能渲染不等于存储标签正确。
- 在原生模拟器接受元素前完成必要注册。记录真实加载顺序，独立检查 YAML 定义、Substance 创建、Entry 复制、最终材质绑定及实体创建。
- 材质可能在早期未完成绑定。不要对 null 的原版 material 调用 new Material；验证来源模板、最终 shader/texture、Assets 材质索引和自身 Substance 的最终绑定。只修改自己独立材质，不修改原版共享材质。
- 保留原版合理分类，检查 MaterialCategories；不要把 Gas、Solid 之类状态标签误当有效材料分类。不要随意添加 Water 等通用配方标签，否则厕所/食谱可能消费新液体。

## 3. 物理参数和相变

明确液固气状态、热容、导热、摩尔质量、质量/密度字段、流动/黏度、颜色与疾病承载，理解游戏字段单位与现实模型区别。不凭名称认为某字段支持真实物理。

按设计定义全部有效相变与副产物，包括阈值和回差。对于需要闭环身份的元素，逐一验证冻结、融化、沸腾、冷凝目标都保持自定义身份；在 Entry 复制后设置目标不够，还需确认最终解析指针及模拟器结果。

检查气液固在格子、瓶/罐/碎块、管道、储存中的相变。遵循原版损坏、破瓶、泄漏或环境置换规则，除非用户明确要求改变。记录不支持的高温分解、潜热或压力相关沸点，不能宣传为完整真实物理。

## 4. 物流和界面

核对资源列表、材料筛选、储物箱、扫地工具、自动清扫器、运输轨道、液体装桶器/倒液体、气体装罐与释放、各类元素过滤器和沙盒生成。根据原生列表实际生成机制修复正确源头，不为每张界面写独立补丁。

容器可以沿用合法原生瓶形并作专属着色/标识；为成熟发布完善自定义辨识与动画状态。不要用液滴 UI 图代替整套容器动画。检查缩略图、拾取动作、翻瓶动作及液面/颜色表现。

## 5. 最低端到端验收

生成环境物质 → 擦拭/捕集 → 地面出现可选中的物品 → 小人搬运 → 储存或装桶 → 倒出/释放回环境 → 管道消费 → 再次保存读取。

记录每步的元素 ID、质量、温度、疾病和是否可选中。测试空容量、部分质量、混合物、错误材料、极端温度、相变以及重复存读。质量减少必须有设计去向；不得因为缺 Prefab 无声丢弃。
