## 这个 skill 能做什么

一句话：**让 AI 以《缺氧》开发者视角设计、实现、调试、审查和交付 Oxygen Not Included Mod**——不是"写完能编译"就收工，而是补齐瓶装实体、房间标签、调优链路、占地对齐、存档兼容这些没被点名但缺了就不能玩的部分。

具体能帮你做这些事：

- **新增游戏内容**：建筑、元素（液体/气体/固体）、物品、配方、植物、动物、疾病、房间、自动化、运输、火箭、世界生成。
- **接通完整系统链**：发现与研究 → 建造 → 搬运/连接 → 使用/生产 → 环境交互 → 保存读取 → 拆除返还，逐环节核对身份、质量、温度、疾病与可见反馈。
- **做原版风格的 KAnim 动画与美术**：以真实原版设备为参照对齐格子、原点、光向与材质，而不是画一张概念图了事。
- **审查你已有的 Mod**：对照系统关联清单逐项判定"已通过 / 待验证 / 不适用（原因）"，并主动发现未点名的关联缺口。
- **定位典型故障**：元素哈希错位、材质创建时机崩溃、动画后缀重复、图标问号、建筑悬空、房间不识别……都有真实案例的推导方法。
- **收口验证与交付**：按证据层级记录编译/替身回归/游戏运行/存档验收，检查安装包没有游戏 DLL、日志、密钥或第二份旧 Mod。

**不适合**：非缺氧游戏、只想让 AI 说两句设计思路不落地实现、以及"你随便帮我编个 API"——本 skill 要求先查目标版本的真实接口再下笔，拿不到游戏时如实标注待实测。

## 它解决什么问题

缺氧是个所有系统互相咬合的游戏：一个"新元素"同时是环境物质、可搬运实体、UI 资源、配方标签四件事。AI 帮你实现时最常见的失败不是写不出代码，而是**只实现了孤立的一层**：

| 表面现象 | 真实根因 |
|---|---|
| 液体在环境里真的能流，但装不进瓶子、擦不成瓶 | 只加了 Element/Substance，没加可搬运实体与原生注册路径 |
| 明明做了 `ui` 动画，游戏里图标还是问号 | animation bank 的 `ui` 状态 ≠ build symbol 的 `ui` 符号，不是一回事 |
| 机器在发电，但不被识别为「发电厂」建筑 | 漏了 `PowerBuilding` 等房间分类标签——发电、房间分类、可调优是三个独立维度 |
| 画布比例看着正确，游戏里建筑却悬空 | 600×400 画布 ≠ 6×4 占地，透明留白、原点与控制器 scale 没在格子上校准 |
| 日志里 Element 与 Substance 查找错位，渲染找不到材质 | 把元素十进制哈希的数字字符串当 `elementId`，被再次哈希 |

这些案例来自一个真实重水 Mod（WHHW_7A5C）的调试经历，都被沉淀进了 skill 的[故障案例库](references/failure-lessons.md)。普通做法为什么不行：通用教程只讲"怎么加一个东西"，不管它接入系统后会发生什么；AI 凭记忆写接口，出错后你得到的是"编译通过"的假安心。

这个 skill 换了什么思路：**先建立系统关联清单再实现，先分层记录证据再宣称完成。** 18 类系统逐项判定适用性，编译/静态/替身/游戏/存档五级证据分开记，"应该可以"不算证据。

> ⚠️ **诚实原则**：没有运行游戏就明确说没有运行；拿不到游戏环境只能给"资源预验收通过，游戏视觉待验证"，绝不编造通过结果。

## 效果示例

**系统关联清单（节选）**——每行包含"关联点、期望行为、实现位置、验证方法、证据、状态"，状态只用 `已通过 / 待验证 / 不适用（原因）`：

| 系统 | 必须思考的关联与边界 | 状态 |
|---|---|---|
| 身份与注册 | 唯一稳定 ID、Tag、哈希、Prefab、Substance、加载顺序 | 待验证 |
| 可搬运形态 | 液体瓶、气体罐、固体碎块、相变、搬运和倾倒 | 已通过 |
| 电力与自动化 | 消费/发电、容量、红绿信号、停机反馈 | 不适用（无电气接口） |

完整 18 类见 [`references/system-integration.md`](references/system-integration.md)。

**美术发布关卡**——禁止占位图、问号图标、简单放大像素冒充成熟美术；必须过"原版并排对比 → 格子占地对齐 → 全状态动画 → 菜单缩略图"整条验收链，任何一项不通过就继续精修。

## 快速开始

```bash
git clone https://github.com/wh520-wh/create-oxygennotincluded-mod ~/.claude/skills/create-oxygennotincluded-mod
```

> Windows 下 `~/.claude/skills/` 实际是 `C:\Users\<你>\.claude\skills\`。仓库自带 [`agents/openai.yaml`](agents/openai.yaml)，Codex 等读取 agents 目录的宿主也可直接使用。

装完对 Agent 说：

```text
帮我做一个缺氧 mod，加一种叫「重水」的新液体，小人能装瓶搬运。
```

Agent 会：恢复你的需求与目标版本 → 找原版最接近的液体与边界案例 → 建立集成审查表 → 设计完整生命周期 → 按原生路线实现元素/实体/注册/资源/本地化 → 校准并打磨美术 → 分层验证 → 出安装包和中文说明，中途对拿不到的验证项如实标"待验证"。

> 仓库地址：https://github.com/wh520-wh/create-oxygennotincluded-mod

## 它和同类有什么不同

| 维度 | 通用「帮我写个缺氧 mod」 | 单点教程 / 社区示例 | **本 skill** |
|---|---|---|---|
| 系统关联 | 只实现点名的功能 | 只覆盖教程主题 | **18 类关联逐项判定：已通过 / 待验证 / 不适用（原因）** |
| 证据标准 | 「应该可以」 | 不涉及 | **编译/静态/替身/游戏/存档 分层记录，缺证据标待验证** |
| 美术 | 占位图、问号图标 | 讲风格不讲验收 | **发布关卡：原版并排、格子对齐、全状态、缩略图，缺一不过** |
| 失败定位 | 反复修表象 | — | **真实故障案例库：哈希错位/材质时机/后缀重复/图标问号…** |
| 范围控制 | 随手改全局 | — | **唯一命名前缀、最小补丁、不承诺与所有 Mod 兼容** |

差异不讲"功能多"，讲"**没被点名的关联也能被发现，没做的验证不会被说成做了**"。

## 工作流程

1. **恢复需求与证据记录**：目标游戏 build、基础版/DLC、程序集来源、现有 Mod、历史失败；先查本地确切代码，不凭记忆补 API。
2. **对照原版最接近的内容**：比较定义、组件、标签、生命周期、动画状态、界面入口和存档行为。
3. **建立集成审查表**：先记录全部类别，再深查适用项。
4. **设计完整生命周期**：为每个状态转移明确身份、质量、温度、疾病、库存和可见反馈。
5. **实现最小完整功能链**：原生组件与行为优先，全局补丁只保留真实必要的。
6. **先校准技术美术再精修外观**：依据格子和原点设计，完成白盒对齐和完整美术关卡。
7. **验证普通路径、极端输入和生命周期**：必要时为历史 bug 写有意义的回归。
8. **依赖、命名、补丁范围、性能和存档升级审查**：生成安装包及清楚的中文说明。
9. **报告实现结果与材料风险**：说明实际验证了什么、尚缺什么，没有运行游戏就说没有运行。

## 验收与测试

本 skill 是流程与纪律型 skill，不含可执行脚本；验证方式是装好后按 [`test-prompts.json`](test-prompts.json) 的 prompt 对话，观察 Agent 行为是否符合每条的 `expected`：

| prompt | 考察点 |
|---|---|
| `smoke-new-liquid` | 冒烟：新液体是否走完"元素 → 瓶装实体 → 搬运 → 释放 → 存读"全链 |
| `integration-gap` | 系统关联：只被点名"加一个物品"，是否主动补查未点名的系统 |
| `art-gate` | 美术关卡：是否拒绝占位图/问号图标，按原版并排与格子对齐验收 |
| `evidence-honesty` | 证据诚实：拿不到游戏环境时是否如实标"待验证"而非宣称通过 |

合格表现的核心不是"功能写出来了"，而是：**主动发现未点名的关联、分层记录证据、缺证据时如实标注。**

## 安全边界

- **不会**给未点名的系统强加功能——但会逐项判定"不适用（原因）"，不静默跳过。
- **不会**用粗糙几何示意图、占位图、问号图标或简单放大像素冒充成熟美术。
- **不会**把编译通过、"机器能发电"、"画出了图片"当成完成。
- **不会**在没有游戏环境时声称"游戏内验证通过"——只允许标"资源预验收通过，游戏视觉待验证"。
- **不会**为一个新元素修改全局 Enum、所有机器或所有房间规则；不承诺与所有 Mod 兼容。
- **不会**未经授权修改用户重要存档；交付前明确备份、升级与回滚路径。
- 用户要求"先分析"时只提交诊断和方案，不修改产品代码。
