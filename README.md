## 这个 skill 能做什么

一句话：**让 AI 带着《缺氧》开发经验做 Mod**——它不用一套强制流程代替判断，而是在实现时提醒那些容易遗漏的关联：瓶罐与碎块、建造蓝图、卡片参数、房间与调优、存档兼容，并让新增内容自然融入原版。

具体能帮你做这些事：

- **新增游戏内容**：建筑、元素、物品、配方、植物、动物、房间、自动化、装备、火箭、世界生成。
- **接通完整功能与玩家反馈**：沿"发现/研究 → 获得/建造 → 搬运/连接 → 使用 → 故障或环境变化 → 保存读取 → 拆除/死亡/相变"推导——元素能流动不代表能装瓶，实体注册不代表可见，能发电不代表房间和调优齐全。
- **做原版风格的美术与动画**：涉及新建或整体重做美术时，先让你选合作方式（完全委托 / 你提供原型 / 先看三个方案）；成熟交付仍以与同类原版同场协调为标准。
- **审查你已有的 Mod**：沿系统关联思路和生命周期主动发现未点名的遗漏，按改动范围深查，不机械全量。
- **定位典型故障**：哈希错位、材质时机、动画后缀、图标问号与巨大、蓝图显示成品、碎块不可见……已确认的事实与"通用风险"分开记录。
- **按风险收口验证与交付**：分清"证据能说明什么"；没运行游戏不写成通过；交付可安装成果、可维护源码和具体待验证项。

**不适合**：非缺氧游戏、只想让 AI 说两句设计思路不落地实现、以及"你随便帮我编个 API"——本 skill 要求先查目标版本的真实接口再下笔，拿不到游戏时如实标注待实测。

## 它解决什么问题

缺氧是个所有系统互相咬合的游戏：一个"新元素"同时是环境物质、可搬运实体、UI 资源、配方标签四件事。AI 帮你实现时最常见的失败不是写不出代码，而是**只实现了孤立的一层**：

| 表面现象 | 真实根因 |
|---|---|
| 液体在环境里真的能流，但装不进瓶子、擦不成瓶 | 只加了 Element/Substance，没加可搬运实体与原生注册路径 |
| 明明做了 `ui` 动画，游戏里图标还是问号 | animation bank 的 `ui` 状态 ≠ build symbol 的 `ui` 符号，不是一回事 |
| 图标不再是问号，却大到盖住旁边的菜单条目 | 图标是独立显示入口：尺寸、居中、遮挡按各入口核对；菜单图不能继承建筑的几何与位移 |
| `place`/`construction` 状态名齐全，放置时却显示完整填色的成品 | 蓝图/施工/成品按原版各阶段分别制作，线稿预览不能用成品图降透明度冒充 |
| 调优后卡片只有固定说明，被误认为增益没生效 | 实测确认增益正常，问题在信息缺失与口径不清——固定说明写基础值，动态值读实际属性，不因此重复加成 |
| 建筑能建造能运行，卡片上却只有名称和描述 | 悬浮卡片、选中面板、效果栏、电路列表与覆盖层按同类原版补齐；固定说明与动态数值来源分开 |
| 元素注册好了、菜单有图标，新冰类材料在环境里却没有外观、挖掘后没有碎块 | 菜单图标、格子外观、掉落碎块、储存形态是不同显示链；"看不到"要分清未生成、不可见还是相变消失 |
| 机器在发电，但不被识别为「发电厂」建筑 | 漏了 `PowerBuilding` 等房间分类标签——发电、房间分类、可调优是三个独立维度 |
| 画布比例看着正确，游戏里建筑却悬空 | 600×400 画布 ≠ 6×4 占地，透明留白、原点与控制器 scale 没在格子上校准 |
| 日志里 Element 与 Substance 查找错位，渲染找不到材质 | 把元素十进制哈希的数字字符串当 `elementId`，被再次哈希 |

这些案例来自一个真实重水 Mod（WHHW_7A5C）及其参考代码的开发调试经历，都沉淀进了 skill 的[故障经验](references/failure-lessons.md)，并按三段记录：已确认的日志或显示问题、从参考实现学到的提醒、**不能写成已发生事实的通用风险**。用户最初怀疑"调优失效"的案例后来被实测推翻（实际为 1.5 倍），记录也随之更正——已排除的故障不继续当问题修补。

这个 skill 换了什么思路：**把《缺氧》开发中容易遗漏的关联和踩过的坑沉淀成经验，让 AI 按需读取、沿生命周期补全，而不是用一套强制流程代替判断。** 关联清单是提醒不是填空题；证据分清能证明什么；通用风险不会伪装成已发生事实。

> ⚠️ **事实与推测分开**：编译通过、资源解析、替身测试各有边界；没有运行游戏就直说。用户实测是有来源的证据——说明是谁在哪个版本确认，不冒充自己执行过。

## 效果示例

**系统关联思路（节选）**——「想到哪些方面」是提醒，不是要求每次填完所有行；不适用的可以跳过，重要但不确定的继续查：

- 身份与发现：独有稳定 ID、Tag、元素/实体对应、研究、菜单、沙盒及百科。
- 物流与存储：环境元素、瓶罐、碎块、种子/蛋、拾取、搬运、清扫器、储存、筛选与释放。
- 信息与外观：悬浮卡片、选中面板、基础/动态参数、状态、覆盖层、图标、动画、特效与声音。
- 保存与世界：存读、拆除、相变、跨世界、DLC、升级与卸载依赖。

完整 11 个方面与生命周期示例见 [`references/system-integration.md`](references/system-integration.md)。

**美术合作方式**——涉及新建或整体重做美术时，正式制作前先选：

1. **完全委托模型**：自行设计、打磨和实现，不必等待中途选方案。
2. **用户提供原型**：先读原型、明确必须保留的外形特征；原型缺失时等待提供，其他独立工作可以继续。
3. **先对齐并选方案**：一次展示至少三个有明显区别的视觉方案（HTML 或图片呈现），选定后再精修实现。

局部修图、排错或沿用已认可原型时，不重复询问。

## 快速开始

```bash
git clone https://github.com/wh520-wh/create-oxygennotincluded-mod ~/.claude/skills/create-oxygennotincluded-mod
```

> Windows 下 `~/.claude/skills/` 实际是 `C:\Users\<你>\.claude\skills\`。仓库自带 [`agents/openai.yaml`](agents/openai.yaml)，Codex 等读取 agents 目录的宿主也可直接使用。

装完对 Agent 说：

```text
帮我做一个缺氧 mod，加一种叫「重水」的新液体，小人能装瓶搬运。
```

Agent 会：涉及新美术时先确认合作方式 → 恢复你的需求与目标版本 → 找最接近的原版对象 → 沿生命周期补齐系统关联并实现 → 按需检查结果 → 交付可安装成果，并说明关键变化、已验证内容与具体待验证项。

> 仓库地址：https://github.com/wh520-wh/create-oxygennotincluded-mod

## 它和同类有什么不同

| 维度 | 通用「帮我写个缺氧 mod」 | 单点教程 / 社区示例 | **本 skill** |
|---|---|---|---|
| 定位 | 只实现点名的功能 | 只覆盖教程主题 | **经验提醒，不强制流程；按内容范围判断关联** |
| 证据 | 「应该可以」 | 不涉及 | **分清"证据能说明什么"；没运行游戏不写成通过，通用风险不写成已发生事实** |
| 美术 | 占位图、问号图标 | 讲风格不讲验收 | **三种合作方式可选；成熟交付以原版同场协调为标准** |
| 失败定位 | 反复修表象 | — | **故障经验分三段：已确认 / 参考提醒 / 通用风险** |
| 范围控制 | 随手改全局 | — | **唯一命名前缀、合理补丁范围、不承诺与所有 Mod 兼容** |

差异不讲"功能多"，讲"**没被点名的关联能想起来，没做的验证不会被说成做了，通用风险不会伪装成事实**"。

## 工作方式

1. **先恢复需求再行动**：了解现有项目、目标游戏版本和用户已定的设计；常规实现自行判断，核心设计无法推断时再询问。
2. **涉及新美术先选合作方式**：完全委托 / 用户提供原型 / 先看三个方案（见[效果示例](#效果示例)）。
3. **按对象按需读取经验**：元素材料读[元素与物品](references/elements-and-items.md)，建筑调优读[建筑与房间](references/buildings-and-rooms.md)，美术动画读[美术与动画](references/art-and-animation.md)，其余类型按需补读；不适用的关联可以跳过，必要关联不能因没被点名而遗漏。
4. **沿生命周期实现**：对输入问从哪里来、对输出问谁使用、对状态问谁看到和如何恢复；接通完整功能与玩家反馈，再打磨细节。
5. **按风险选检查**：局部美术修复看相关资源与显示，身份或存档改动更谨慎；表格、脚本在确有帮助时使用；检查未预期影响时留意共用生成器与同流程对象。
6. **交付可维护成果**：可安装产物 + 可编辑源文件 + 关键变化、已验证内容与具体待验证项；正式交付不以原型冒充成熟版。

## 验收与测试

本 skill 不含可执行脚本；[`test-prompts.json`](test-prompts.json) 是**可选的技能作者评估示例**，不要求每次开发执行；独立试用时只给 prompt、不提前给关注点。12 条覆盖：新液体、发电机与调优、局部图标修复、美术原型、方案选择、已确认调优的信息补全、冰类碎块、植物、动物、装备、世界生成、存档迁移。

合格表现的核心：**没被点名的关联能想起来，没做的验证不会被说成做了，用户澄清或新证据出现后能更新结论。**

## 安全边界

- **不会**在没弄清需求、项目与目标版本前动手；核心设计无法推断时会先问。
- **不会**在用户要求"先分析"时修改产品代码——诊断请求只提交诊断与方案。
- **不会**把简化的美术原型当最终版交付；只有用户明确要原型时才允许简化。
- **不会**把编译通过、资源解析通过或替身测试当成游戏内完成——没运行游戏就直说，不冒充自己执行过用户实测。
- **不会**把标记显示或固定说明当成调优增益接通/失效的结论；以实际属性和实测为准，已确认的结果不反复当故障修补。
- **不会**只提供名称、描述和建造菜单说明就认为卡片信息完整；固定说明与动态数值分开核对。
- **不会**把通用风险写成已发生事实，也不为想象中的问题虚构修复历史。
- **不会**为小改动强制建立庞大检查体系；检查强度与改动风险匹配。
- **不会**为一个新元素修改全局 Enum、所有机器或所有房间规则；不承诺与所有 Mod 兼容。
- **不会**未经授权修改用户重要存档；交付前说明备份、迁移与限制。
